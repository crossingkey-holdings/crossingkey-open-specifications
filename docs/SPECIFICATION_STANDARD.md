# Specification Standard

## Required header

A normative CrossingKey specification should identify:

- title;
- version;
- status (`draft`, `candidate`, `stable`, or `retired`);
- last-updated date;
- scope;
- intended audience.

## Normative requirements

Requirements should be testable or reviewable. Avoid using normative language for aspirations that cannot be evaluated.

## Examples

Examples are informative unless explicitly stated otherwise. Example code must not contain live credentials or imply production readiness without evidence.

## Compatibility

If compatibility is claimed, identify the relevant protocol, version, environment, or dependency boundary.

## Security and authority

Specifications that can produce side effects should identify authorization, ownership, replay, idempotency, and failure considerations where material.
